# Architecture: Content Extensibility

New maps, character designs and weapons will be added often, so adding content must not require changes to core scripts.

- **Maps**: each arena is a self-contained scene under `scenes/arenas/` that owns its geometry, `SpawnPoints`, `ItemSpawns` (`ItemSpawner` nodes) and `Camera2D`. The main scene only loads an arena. A map's `camera_limits` are exactly 640x360, 1280x720 or 2560x1440 (the view at a camera zoom), and the map maker places `CameraShot` nodes (composed views at zoom 3, 1.5 or 0.75) that the camera cuts between; `test_arenas` checks every arena scene. The test arena stays for tests. The game loads the Isles (`isles.tscn`, session 6); the Range (`range.tscn`, a flat floor with measuring lines every 8 px) stays for tuning movement. Map props (`Ladder`, barrels) are scenes under `scenes/props/` with cartoon art; one-way platforms are static bodies (or tiles) with one-way collision.
- **Characters**: one shared `Fighter` scene; a character is a `CharacterData` resource under `data/characters/` (its look) that points to a `FighterClass` resource under `data/classes/` (how it fights: melee combo, later class stats).
- **Weapons**: one shared `Weapon` scene; a weapon is a `WeaponData` resource under `data/weapons/` plus its sprite. Weapons are separate sprites attached to the fighter's hand, never baked into character frames.
- Prefer a new resource or scene over a new code branch when adding content.

# Architecture: Code Rules

- Small, focused scenes and scripts. Movement, combat, weapons, health and animation stay separate.
- Damage and hit detection never depend on sprite art (collision shapes and shape queries only).
- Fighters never read `Input`; a controller (local, bot, remote) provides their intent.
- Use signals where they simplify communication; avoid unnecessary abstractions and dependencies. Use Godot's native 2D physics and animation.
- Build one milestone at a time, run the checks after each one, and do not add features that were not requested.

# Art Pipeline

- **DONT-OPEN/** (user, session 5) holds everything set aside: the Docks map and its art, the street brawler and trenchcoat agent with their cutout rig code (`CharacterRig`, `RigAnimator`, `CoatMesh`) and tests, the item art, Gemini's armoured robot frames and Python tools, reference images, and the user's own drawing folders (`DONT-OPEN/characters/`, `DONT-OPEN/weapons/`, git-ignored). Godot ignores it (`.gdignore`). Never open, read, use or change anything in it unless the user asks.
- Items (weapons, throwables) show flat grey `GradientTexture2D` boxes the size of the old art until real art comes (development step 5); item art is 3x (`ItemData.pixels_per_unit`). Textures import with mipmaps (project importer default) because the camera shrinks the art when it zooms out.
- Map art is cartoon vector art (user, session 6): a generator in `tools/` (e.g. `tools/draw_isles.gd`) writes each picture as an SVG in world px under `art/` and renders it at 3x to a PNG in `assets/`. Pixel art generated by script keeps its `.aseprite` source under `art/`, exported to `assets/` with the Aseprite CLI (`C:\Program Files\Aseprite\Aseprite.exe -b ... --script file.lua`).
- The players are stick figures (user, session 4: the drawn characters are set aside). Their animations are frame by frame: `tools/make_stickman.gd` samples every keyframe clip at 24 fps (at least 12 frames a loop) and draws each frame as its own picture (white body for the character colour, shaded far limbs, dark outline, smears behind fast hands and feet) into `art/stickman/strips/` with a `.json` per clip (timing, front fist per frame) in `assets/characters/stickman/`; then `tools/stickman.lua` (Aseprite CLI) saves one `.aseprite` per clip in `art/stickman/` and exports the strips to `assets/characters/stickman/`. Attack clips also get an untinted `<clip>_fx.png` strip (white wind behind the strike), played behind the body. Rerun both after changing a clip. `FrameAnimator` plays them (`CharacterData.frames_dir`).
- The game's players use the Mucho Pixels character pack (user, session 7; the stick figure stays for tests and as the timing reference). Its licence forbids redistribution and this repo is public, so the pack's zip stays outside the repo and its clips in `assets/characters/mucho_*/` are git-ignored: `tools/import_mucho.gd` makes them per checkout (`<godot> --headless --path . -s res://tools/import_mucho.gd -- <pack zip>`, then reimport). It scales the frames to 3x and builds the clips the pack lacks from its frames; change the importer, not its output. Never commit pack art.
- Character animations are keyframe clips in `assets/animations/` (format: `docs/CHARACTER_ANIMATION_SPEC.md`), drawn into the stick figure's frames. Clips Claude makes come from `tools/make_animations.gd` (`<godot> --headless --path . -s res://tools/make_animations.gd`); change the generator, not the JSON. Motion capture sources (CMU BVH) live in `art/mocap/` and are read by `tools/mocap.gd`. The stick figure's skeleton (pivots and leg sizes) is `art/stickman/rig/`.
- `art/` is excluded from Godot import (`.gdignore`).

- Reimport after adding scripts or assets: `<godot> --headless --path . --import`
- Run every suite (Git Bash): `tests/run_all.sh`; one or more: `tests/run_all.sh test_melee test_pickup`. Exit code 0 = all passed.
- A single suite by hand: `<godot> --headless --fixed-fps 60 --path . -s res://tests/<test_name>.gd`. `--fixed-fps 60` runs physics as fast as possible instead of in real time (about 12x faster).
- Suites extend `tests/test_case.gd`, which fails the suite on any engine or script error, not only on failed checks.
- Suites that load `main.tscn` need the Mucho clips: on a fresh clone run `tools/import_mucho.gd` first, or they fail with "no frame clips".

# Commit Conventions

- Split work that would normally fit in a single commit into 4-5 small, logically separate commits.
- Each commit must be atomic: one concern per commit (e.g. scaffolding, core logic, tests, docs, config), and the project should build and pass checks after every commit.
- Follow the global message rules: imperative mood, subject under 72 characters.
